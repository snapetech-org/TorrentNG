TorrentNG: why the recent changes have not established a performance win

The next work should change how transfers are scheduled and how long memory is retained. Several recent fixes reduce small costs while leaving repeated storage handoffs, per-block control work, and retained caches in place. There is also a reproduced rate-scheduler liveness defect that can stop useful transfers despite available credit.

Confidence: high in the reproduced scheduler failure and the inspected ownership/control paths; moderate that storage handoffs are a major component of the seed CPU gap; unknown for their exact share of full-client CPU until the current binary is profiled.

This audit executed the original rate-scheduler code in an isolated Rust harness, ran its 19 existing tests, and measured a separate worker-handoff mechanism. It did not run the full daemon or a new five-client comparison. The included source files are unmodified copies of the reviewed commit.

1. What is already fixed, and why it could leave the score nearly unchanged

0f726a89 adds owner-backed pooled payloads, replaces the database worker's idle timeout polling, conditions the DHT retry timer on pending forwards, and stops treating every future disk deadline as immediately urgent. Those were real changes. The earlier completion-forwarding task and copying TCP upload encoder are also gone.

However, the 4 MiB/s receiver cap largely determines completion time. A verified 198.4-second run versus 198.1 seconds says the clients delivered the same capped workload successfully. It is not a measurement of their maximum transfer capacity. Thin-LTO image-build CPU is outside those timed windows.

At 16 KiB blocks there are 65,536 blocks per GiB. A reduction of one microsecond per block saves only 0.0655 CPU-seconds/GiB. The published candidate's 3.97 CPU-seconds/GiB corresponds to roughly 60.6 microseconds per block, including all client background work. Closing a multi-second gap requires removing substantial repeated work, not merely one small allocation or memory copy.

The old report's eight-second idle window measured about 0.065% of one core for TorrentNG versus about 1.49% during seeding. Extrapolating that idle rate would explain roughly 4% of the active CPU, not the full gap. That short window is insufficient for precise attribution, but it shows why idle timer repairs were never a complete active-CPU plan.

Lowering a buffer-pool maximum from 84 MiB to 16 MiB cannot reduce measured RSS when the workload never approaches the old limit. Reusing buffers can reduce allocation cost while retaining more memory between operations. These changes have different objectives.

2. Reproduced defect: cancelled demand can block an eligible peer

High confidence: executable reproduction against the unmodified production RateTree module.
Contribution to the observed public-swarm plateau: moderate hypothesis, requiring a live trace. Contribution to one-peer seed CPU: not established by this two-peer case.

RateTree::try_grant_tracked() registers a peer in the waiting index after a denial. It later prevents another peer from advancing more than 32 KiB beyond that waiter's virtual progress. The waiting entry is cleared by a successful grant or peer removal; it has no independently owned demand lifetime.

The live choke handler marks the peer choked and reconciles requests, but does not retire its rate waiter. Subsequent refills return immediately for a choked peer. In HierarchicalRateService::acquire(), cancellation can likewise return without clearing pending demand. The compatibility adapter removes its temporary peer registration, which explains why its cancellation test does not protect the long-lived peer path.

The reproduction spends the initial credit, lets peer B receive a denial, then stops retrying B while it stays registered. After allowing credit to refill, it makes 1,000 attempts for peer A. A control case removes B before the same retry sequence.

CaseA grantsA denialsRequested retry delay
B stays registered but no longer requests service01,0001 ns on the final retry
Remove B before the same retries1,0000None

All 19 existing RateTree tests passed. The missing case is the relationship between demand cancellation and a connection that remains alive. A timer does not repair stale demand; it just retries it. The runtime's actual timer resolution is not one nanosecond, but requesting another near-immediate wake can repeatedly run the refill path.

Repair: give pending demand its own lifetime, separate from peer registration and issued grants. Retire it when demand stops being runnable. Fairness should distribute service among runnable demands; an absent demand must not hold the service idle. Keep outstanding grants and refund epochs intact. Multiple upload futures for one peer require correct ownership or reference counting. The control case's peer removal is diagnostic, not the proposed fix.

Run bash repro/run_checks.sh. See captured results and reproduction source.

3. Active CPU: two storage round trips remain in the common miss path

High confidence in topology; moderate confidence in whole-client impact. The normal upload read follows these steps:

  1. The peer owns an upload obligation and acquires read and payload admission.
  2. read_owned_at_with_priority() acquires class/mount credits and creates a preparation job.
  3. The preparation worker normalizes the path, opens or touches the descriptor catalog, checks identity, and looks in the read cache.
  4. The completion wakes the peer runtime. A cache hit still paid this worker round trip.
  5. On a miss, the peer runtime acquires device admission, acquires a frame, constructs operation ownership, and submits another job to the backend.
  6. The backend completes, waking the peer runtime again. The path is checked again, counters/cache are updated, and the frame becomes payload.
  7. Rate admission, socket transmission, grant settlement, obligation completion, and resource release follow.

scheduler.rs contains the preparation channel and boxed job in BlockingPool::run(), another backend completion, path allocations and identity checks, and per-operation ownership wrappers. handle_cache.rs validates and refreshes its catalog entry on a hit. Removing one completion-forwarding task left this topology intact.

I measured the cost of that mechanism on this environment. Each variant processes 256 MiB of useful warm-file reads, normalized to a GiB; three repeats rotate the variant order. The first three use the same 16 KiB reads and two path metadata checks. CPU time includes the process's worker threads.

These are not TorrentNG scores or a measured application speedup. The experiment uses std channels, no Tokio/socket traffic, a warm 16 MiB file, and sequential dispatch. Batching also amortizes metadata checks. Concurrent production work may amortize handoffs differently. The useful result is the order of magnitude: task/worker crossings can cost much more than the actual warm read.

A separate isolated test of the actual rate core, including its three uncontended mutex acquisitions for grant/settle/refund, took about 0.025 wall-seconds/GiB for a single peer. That does not include asynchronous waits or contention, but it argues against treating a few BTreeMap operations as the main cause of the one-peer seed gap.

Refactor: one bounded storage service should own descriptor/cache preparation and I/O through a single completion. Batch already queued adjacent demand. A shared allocation can feed separate Piece responses with per-block cancellation and accounting. Preserve file replacement and no-follow protections, but amortize their work across explicit batches. Avoid synchronous path checks on the Tokio reactor. Do not implement a second unbounded cache to make this look faster.

Evidence: mechanism source, raw measurements, summary.

4. io_uring has additional costs to verify against the selected backend

High confidence in code; unknown contribution to benchmark CPU. The committed candidate score reports do not establish which backend and fixed-buffer path were active. Record that once outside the clean measurement window.

In register_file_slot()/release_file_slot(), a descriptor enters the fixed-file table on demand and is removed when its last in-flight reference ends. An isolated operation can therefore add a registration update and an unregister update. Concurrent operations share the entry, but quiet gaps discard it. A fixed-file feature intended to amortize descriptor work can add work at low queue depth.

Compare ordinary FD submissions with a bounded persistent fixed-file cache. Retaining a slot requires retaining its leased descriptor and correct access/generation identity; the present numeric-FD key is safe only because the descriptor is held while the operation is live. Keeping that key after dropping the handle would introduce reuse bugs.

The scheduler also acquires an ordinary vector-backed frame before the ring chooses a registered buffer. The fixed read writes into the latter. On success, Frame::into_registered_slot() replaces the ordinary backing with Empty, dropping it rather than returning it to the pool. Choose one actual backing before dispatch, with its ownership and budget attached.

There are four 256 KiB registered slots per ring. The new owner-backed Bytes correctly keeps slots alive through use, but a long-lived read-ahead cache can hold those slots and force later operations onto the ordinary-buffer fallback. Measure slot occupancy and lifetime before assuming registered buffers are the fast path throughout a run.

5. RAM: the working set and retention policy remain largely unchanged

High confidence in the retention design; unknown exact allocation breakdown of the latest unpublished run. Your supplied exact-906 numbers already show lower seed anonymous memory than qBittorrent, Transmission and Deluge: 14.7 MiB versus 22.5, 20.6 and 85.1 MiB. rTorrent remains lower at 1.9 MiB. Those exact-source reports were not present on fetched main, so they are treated as user-provided measurements, not independently verified artifacts.

TorrentTask::new creates its own MountScheduler; the constructor creates its own PeerReadCache. Default cache capacity is not preallocated, and the shared governor prevents unrestricted growth, but memory can accumulate across live torrents until those bounds are reached. The cache's last-used timestamp drives replacement order; there is no time-based or pressure-triggered eviction inside that cache. Writes, replacement checks, eviction on insertion, or scheduler teardown can remove entries.

The cache reserves MemoryClass::PeerBuffer, the same class required by useful peer payload and wire work. Optional data therefore competes with mandatory data. Cache insertion tries to reserve new memory before evicting replacement victims. Under pressure it can fail admission while retaining reusable or discardable old data. This is a dense-workload concern, not an established cause of the one-ISO sample.

A second retention layer matters: clearing cache entries can simply return their allocations into the frame pool's 16 MiB idle reserve. A smaller cache gauge then does not necessarily produce a smaller process. Pressure eviction must coordinate with pool trimming. A remaining Bytes slice can also pin a larger backing allocation after its cache entry is gone.

The older published cache-off probe was 7.4 MiB anonymous versus 16.3 MiB in the full candidate pass. Different host loads and single runs prevent causal attribution, but this is a stronger lead for memory than reducing an unused cap. Frame reuse and correct charge lifetime should be kept; add a global reclaimable cache budget, explicit pressure/lull trimming, and actual backing-capacity accounting.

Assess fresh idle, post-transfer idle, long-lived connections, and many loaded torrents separately. Anonymous RAM, mapped file pages, page cache, socket memory and PSS answer different questions. Large RSS with low anonymous memory is not inherently inconsistent: mappings and shared pages can account for the difference.

6. Downloading still pays for writing and then rereading payload

High confidence in the default path; impact unmeasured after fixing liveness. The default piece-assembly budget is zero. TCP Message::parse() copies Piece data. write_transfer_block() sends received blocks through individual storage work. Completed pieces then enter verify_transfer_piece(), whose non-assembled branch uses PieceVerifier to read the file back for hashing.

Page-cache hits may keep those extra reads out of physical io.stat, but they still require logical reads, buffers, queueing, and hashing work. A bounded global assembly/receive budget can hash bytes already in memory and coalesce writes. It needs a correct spill path for large pieces and out-of-order blocks, so this is a controlled architectural experiment rather than simply raising a per-torrent RAM limit.

The existing public result near 5% cannot validate full-download peak memory or maximum throughput. Fix the runnable-demand defect and use a controlled private download fixture before tuning request windows, disk pressure thresholds, or assembly sizes.

7. The next implementation sequence

  1. Fix rate-demand lifetime and fairness wakeups. Add live-adapter regressions covering choke, cancellation, no useful work and concurrent waiters. Reproduce the live stall with a private two-seeder fixture.
  2. Profile the exact current binary during verified seeding. Separate user/system CPU and threads. Record backend selection, worker dispatches and context switches. This establishes which mechanisms actually dominate.
  3. Fuse storage preparation and backend dispatch. One completion and bounded batches for already queued work. Measure this independently.
  4. Repair backend-specific amortization. Fixed-file lifetime and buffer choice if io_uring is in use.
  5. Make optional memory globally reclaimable. Coordinate cache eviction with frame-pool trimming and preserve all live views.
  6. Improve the download receive/hash/write pipeline. Test small global assembly budgets after download liveness works.

The detailed file-level instructions and regression requirements are in IMPLEMENTATION-HANDOFF.txt.

Use clean comparative runs separately from diagnostic profiling. A rate ladder, such as 4/32/128 MiB/s and uncapped where feasible, can distinguish background CPU per second from cost per useful byte. Use the same hash-verified payload, memory pressure, cache state, protocol, encryption and peer count. Alternate baseline/candidate before repeating all five clients. Include completed-download peak RAM as well as seeding RAM.

Assessment: the project can plausibly improve substantially by eliminating repeated worker crossings and unnecessary retained data. The reproduced liveness problem warrants repair regardless of the benchmark score. Rust provides the tools to implement this efficiently, but the current architecture still schedules and accounts for a small block as several separate jobs. The exact improvement and the ability to beat every competitor remain unknown until the refactored path is measured.
