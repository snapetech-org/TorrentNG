# Observation artifacts

The summaries, client logs, and raw `smaps`/metrics diagnostics are the retained
run evidence. Temporary session databases and local API/bootstrap tokens are
excluded. Generated payload copies are excluded because some are 128 or 256
MiB, larger than GitHub's single-file limit, and the probe can regenerate them
from the recorded size and deterministic seed. The archived runs used seed
`20261022` (the probe default). Their payload hashes are recorded in each
summary and in the report. Current probe summaries also record `fixture_seed`
explicitly.

For runs that include rTorrent, install the pinned Python helper dependencies
with python3 -m pip install -r scripts/transfer_rebuild/requirements.txt.
The SCGI response parser uses defusedxml to prevent XML entity expansion.

Payloads can be regenerated by rerunning
[`native_seed_cpu_ram_probe.py`](../../../../scripts/native_seed_cpu_ram_probe.py)
with the same `--size` and `--seed 20261022`. The matched rTorrent binary and
runtime libraries remain task-local benchmark inputs and are identified by
their hashes and paths in the summaries.

The `upload-coalesce-16ms/` directory preserves the source-matched 8 ms and
16 ms release and PGO binaries (gzip-compressed with uncompressed SHA-256
checksums), raw and normalized run summaries, client logs, configs with
generated credentials redacted, fixture metainfo, metrics, and compressed
process smaps. The 16 MiB debug traces retain the per-batch event logs used to
count storage reads and Piece frames. Generated payload copies and temporary
session databases/tokens remain excluded.

`pgo-current-source-16ms-20261022/` preserves two clean-source PGO retraining
approaches. Its five-pair transfer-window profile screen improved CPU and
anonymous memory but raised PSS; the one-pair full-process profile screen lost
on all three resource metrics. Both remain opt-in experiments with exact
profiles, binaries, summaries, logs, metrics, compressed smaps, and checksums.

`upload-rate-batch-20261022/` preserves a candidate that reserved a bounded
group of per-block upload-rate grants under one rate-tree lock. Two randomized
64 MiB screens did not establish a CPU and PSS improvement together, so the
candidate was not promoted. Its patch, executable, verified summaries, logs,
metrics, and process maps remain available for future profiling.

`low-risk-tuning-screen-20261022/` preserves six one-round verified 64 MiB
screens of jemalloc, one-arena and immediate-decay jemalloc refinements,
host-tuned codegen, Rust 1.97, and `opt-level=3`, plus a 256 MiB diagnostic CPU
profile of the current system-allocator baseline. None of the candidates
reduced CPU and PSS together; no release default changed. Exact binaries and
raw summaries are retained with the results.

`mapped-window-read-probe-20261022/` retains a hot-file microprobe comparing
64 KiB `pread` batches with 64 KiB and 1 MiB mmap windows. The 1 MiB mapping
reduced median read-only CPU by 8.6% in three small pairs; scheduler, socket,
cold-file, and memory costs were not measured.

`pgo-native-target-screen-20261022/` preserves a profile generated and used
with the same `target-cpu=native` setting. Its one-round 64 MiB screen lost to
the retained PGO control on CPU and PSS, while anonymous memory was slightly
lower. The exact profile, executable, instrumented binary, verified run
summary, logs, metrics, and compressed process maps are retained; no default
changed.

`pgo-profile-blend-20261022/` preserves an equal-weight combination of the
current-source full-process and transfer-window profiles. A one-round screen
looked better, but three randomized rounds used more CPU and PSS than the
retained PGO control. The initial and repeated verified summaries, exact
merged profile, candidate binary, logs, metrics, and compressed process maps
are retained so the tradeoff can be revisited.

`runtime-tuning-screen-20261022/` preserves a fat-LTO PGO screen and glibc
arena-cap screens. Fat LTO reduced executable size but used more CPU and PSS.
`MALLOC_ARENA_MAX=1` reduced PSS and anonymous memory in three rounds while
raising median CPU by 5.4%; cap 2 raised CPU by 42.3% in its one-round screen.
The archive includes exact summaries and diagnostics plus the fat-LTO binary.
No production or build default changed.

`io-worker-count-screen-20261023/` preserves a config-only comparison of one
versus two shared storage I/O workers on the current source. One worker lowered
CPU and memory in three single-peer rounds, then used 12–19% more CPU in each of
three randomized rounds with three concurrent peers while lowering memory.
Keep the production default at two. The follow-up
[`lazy-worker-trigger-screen-20261023/`](lazy-worker-trigger-screen-20261023/)
preserves two lazy-worker prototypes; neither started worker two under the
three-peer workload, and neither showed a repeatable CPU/PSS improvement.

[`mapped-window-writev-probe-20261023/`](mapped-window-writev-probe-20261023/)
compares a 128 KiB `pread` buffer and a 1 MiB mmap window when both feed the
same eight-frame loopback `writev` path. The four counter-balanced pairs had
mixed CPU results and no memory measurement, so the mmap path remains a
microprobe rather than a production candidate.

The later `MALLOC_ARENA_MAX=1` three-peer follow-up is also captured in
[`arena-cap-concurrent-followup-20261023/`](arena-cap-concurrent-followup-20261023/):
it reduced memory but increased CPU in all three randomized rounds, replacing
the earlier high-load, one-round inconclusive description.

`pgo-hotpath-profile-20261022/` retains one exact-binary 256 MiB PGO CPU
profile. It did not provide a matched performance result; the peer-read stream
map was not a sampled symbol, so a map-only refactor was not selected.

`io-uring-queue-depth-followup-20261022/` preserves the depth-1 failure and
depth-4/depth-8 screens. One-pair depth-4 runs looked faster, but a randomized
three-pair 64 MiB repeat used 7.3% more median CPU than `pread`, with tied PSS.
Raw summaries, run logs, redacted configurations, fixture metainfo, and the
queue-full failure are retained; generated payloads and temporary credentials
are excluded. No queue depth or release default changed.

`pgo-hotpath-profile-20261022/libc.debug.gz` preserves the exact matching libc
debug ELF used to resolve the profile samples. Its uncompressed SHA-256 and
build ID are recorded in that observation's README.
