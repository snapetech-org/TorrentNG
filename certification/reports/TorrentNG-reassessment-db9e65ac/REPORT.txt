TorrentNG reassessment — current main db9e65ac
Reviewed 2026-10-21

DECISION

There is substantial implemented work, but the earlier handoff is not complete. The main remaining CPU issue to attack is the amount of scheduling, allocation, file lookup, admission and completion work performed for every 16 KiB block. The previous change removed one storage round trip; it did not amortize the remaining round trip across blocks or make cache hits cheap. This audit exercised the actual current storage crate, rather than repeating the previous synthetic channel experiment.

Confidence: high in the source dispositions and reproduced allocation/retention behavior; moderate that coarser operations are the best next CPU target; unknown how much whole-daemon improvement any proposed change will produce. No current-head five-client benchmark was run here. The main checkout remains clean. Experimental changes exist only in an isolated copy and in the attached patch.

PRIOR FEEDBACK: WHAT LANDED

1. Stale rate demand: implemented in bf37a33. Pending synchronous and asynchronous demand now has a lifecycle separate from peer registration and unsettled grants. Fairness-only waits use progress notifications instead of 1 ns retries. V1, V2 and webseed integration is present. I independently compiled the unmodified current RateTree and ran its 22 tests; all passed, including retiring live-peer demand and preserving sibling demands. The requested private two-seeder daemon fixture is still missing. The unchanged old archived reproducer demonstrates the old source, not a failure of the current fix.

2. Fused portable storage reads: implemented in 457df45. Descriptor preparation, cache lookup, positioned read and completion validation share one pread worker job. This is meaningful progress. Cache hits still acquire mount/device admission, allocate an operation and go through that worker. Requests are still individually submitted. io_uring retains its separate route.

3. Cross-torrent cache budget and reclamation: implemented in 457df45. There is a process-wide 16 MiB backing budget, per-scheduler limits, governor-scoped reclamation, alias-lifetime ownership and idle-pool trimming under pressure. This bounds growth; it does not establish low steady-state memory or make consumed sequential ranges disappear promptly. Multi-torrent pressure qualification remains open.

4. Upload context sharing, concrete upload futures and combined settlement: implemented. These remove repeated context cloning, an outer future box, and a redundant zero-refund lock respectively. FuturesUnordered still allocates a node for each operation. There is no repeated, matched evidence establishing the individual CPU savings.

5. Codec memory and parsing: partial completion. Empty oversized buffers now trim opportunistically, and owned TCP Piece decoding removes the extra payload copy. The retained read-copy credit remains at its lifetime high-water mark. The default process-wide piece-assembly allowance remains zero; the 0/4/8 MiB download experiment has not happened. The new incoming-Piece copy elimination does not directly remove work from the one-peer seeding data path.

6. io_uring fixed-file churn and buffer selection: still open, but deprioritized for the measured problem. The newer complete comparison positively identifies pread, without registered files or fixed buffers. io_uring changes cannot explain an improvement in that run.

NEW FINDING 1: CHEAP DATA, EXPENSIVE PER-BLOCK OPERATIONS

High confidence in mechanism; moderate confidence in prioritization; unknown whole-daemon gain.

The probe directly calls current MountScheduler::read_at, with pread forced, the real governor, two Tokio workers and the default storage worker settings. It uses a warm 16 MiB file, one sequential caller, three rotated repeats and process CPU time including workers. The initial variants each read 64 MiB. An allocator counter records allocations across worker threads. It is a storage-only diagnostic, with no sockets, actor, rate service or live swarm; the compiler target is GNU/glibc, unlike the musl daemon image. Timings include the small counting overhead. Do not compare these absolute scores with the daemon table.

Variant                         Median CPU-s/GiB   Allocations/read
16 KiB, default read-ahead       2.023              12.20
16 KiB, cache disabled           2.008              13.00
256 KiB, cache disabled          0.195              13.00

Default cache hits were 3,956 of 4,096 measured requests (96.6%). Nevertheless, the default path still made approximately 12 heap allocations per read. Cache-disabled 256 KiB requests keep about the same administration per operation but amortize it over sixteen times the payload. The result is strong evidence for changing operation granularity. It is NOT evidence for tenfold whole-client acceleration or a reason to send oversized BitTorrent wire requests.

Source explains the work: read_owned_at_with_priority takes class admission, copies paths, clones owners, reserves a DiskSubmission and device permit, then submits PreparedPread. Even a cache hit enters the file catalog, takes its locks and checks path identity; the completion checks identity again. The source contains two path identity checks on a warm catalog/cache hit. Runtime syscall counts were not collected: strace was installed, but ptrace was denied by this environment.

Next change: collect already queued compatible upload requests, use one bounded storage operation and file lease for a 64–256 KiB extent, and return individual 16 KiB views with their request identities. Batch ready socket writes separately. Keep cancellation, fairness, per-request settlement and path-replacement fences. A generation-validated cache/file owner can eliminate repeated catalog construction; batch validation must retain the existing replacement guarantees. Do not add disk waits to Tokio workers or remove identity checks without a replacement lifetime model.

NEW FINDING 2: DEFAULT READ-AHEAD BYPASSES THE POOL

High confidence; reproduced on current code.

StorageIoConfig defaults to a maximum read-ahead of 512 KiB. FramePool size classes end at 256 KiB. Larger requests use a fresh zeroed Vec and are not pooled on release. Thus the existing pooled-Bytes ownership improvement does not recycle the largest default read-ahead allocations.

In 256 MiB probes the baseline allocated about 276.3 MB cumulatively across about 199,953 allocation/reallocation events. An isolated candidate adds a 512 KiB class and retains at most two idle buffers in that new class, preserving the existing active and total-idle caps. It allocated about 25.2 MB, a 91% reduction in allocated bytes, but still performed about 199,475 allocation events. The allocation count scarcely changed because the per-block operation objects remain.

The bounded candidate's three-repeat median was 1.704 versus 1.769 CPU-s/GiB for its paired baseline, a small result with overlapping ranges. A separate unrestricted-class pair was 1.732 versus 1.758. Neither establishes a meaningful daemon speedup. Merely reducing read-ahead to 256 KiB reduced allocated bytes but was slower in its separate probe and is not recommended from this evidence.

Memory tradeoff matters. Adding the class without a small class-specific retention cap left about 9.39 MiB in the idle pool after the scheduler was dropped, versus 0.89 MiB for baseline. The two-buffer cap held this to about 1.89 MiB. Those are pool allocation capacities, not measured RSS. The added class also rounds requests above 256 KiB up to 512 KiB, increasing some backing charges; near-cap admission behavior must be checked. The included patch is an experimental candidate, not an accepted production optimization; it still needs daemon and burst/concurrency testing. Three focused tests passed: aliases retain charges, burst retention stays bounded, and generic reuse clears old contents.

NEW FINDING 3: THE CACHE BUDGET DOES NOT TARGET WORKING-SET SIZE

High confidence in retention behavior; unknown contribution to the benchmark's 25 MiB anonymous peak.

In the sequential probe the default cache retained about 7.64 MiB of logical payload and 7.75 MiB of backing allocations after the measured reads. A 512 KiB cache configuration had a similar hit fraction in this simple stream while retaining much less, but this does not qualify that default for random or multi-peer traffic. The cache removes entries on capacity pressure, invalidation or scheduler destruction; it does not track that a forward range has been completely consumed by its only reader. Global caps therefore prevent multiplication across torrents without reducing this one-torrent retained payload.

Separate transient forward-read windows from a reusable multi-peer hot-range cache. Retire consumed windows when no readers retain them; retain older ranges only when there is observed reuse. Combine pressure/lull eviction with a no-retain or trimmed return to the frame pool. Otherwise cache reclamation can become idle-pool retention. Report cache payload, backing allocations, active pool bytes, idle pool bytes, governor credit and process memory separately; some of these overlap and must not be summed.

NEW FINDING 4: CODEC TRIMMING LEAVES STALE CREDIT

High confidence in reproduced credit behavior; unknown effect in ordinary seed workload.

A current-code codec probe decoded a 512 KiB extension message, dropped the returned message, and invoked the empty-buffer trim. The remaining input buffer had 65,536 bytes capacity, but the governor still charged 589,830 bytes. One hundred further empty decodes did not reduce the charge; dropping the codec returned it to zero. This is conservative retained admission credit, not proof that 589,830 bytes of physical RAM remain allocated.

The code cannot release read_copy_high_water_bytes because the lease belongs to the connection rather than the returned message. Move payload/backing credit into the object that owns the emitted data, with clone/slice lifetime accounting. The new zero-copy Piece path makes accounting for full backing capacity particularly important. Do not simply shrink the credit while a caller can still hold a message.

SMALLER FOLLOW-UP: RATE FAST PATH

The stale-demand fix added a per-torrent notification-map lookup and RateDemandGuard. Every successful asynchronous acquisition still drops that guard and takes the tree lock to retire demand already cleared by the successful grant. Delay allocating notification/wait state until denial, and disarm the guard when the grant has already cleared its demand. Preserve sibling-demand cancellation and the post-grant cancellation/refund check. This is a verified source opportunity, not a measured main CPU cause. Do not let it replace the batching work.

HOW TO RESTART IMPLEMENTATION

1. Treat db9e65a as the source baseline, recover or regenerate the missing raw diagnostic profile, and use a fixed local verified fixture independent of public-swarm success. Preserve every candidate patch and source identity.
2. Finish the private download regression with at least two controlled seeders and forced choke/cancel transitions. Record useful blocks, outstanding requests, fairness wait reasons, write/verify progress and completed hashes. This decides whether the remaining download issue is rate scheduling, requestability, transport, or storage backpressure.
3. Implement bounded batching and stable file/operation ownership in the pread upload path. Measure dispatches, allocation events, path checks, completions and context switches per GiB; keep wire requests at legal sizes. The goal is fewer administrative operations per useful GiB.
4. Test the attached bounded pool candidate as an isolated experiment, then the forward-window/reuse cache policy and codec owner accounting. Require both CPU and retained-memory evidence before keeping an allocator/cache change.
5. For profiling, collect user and kernel CPU, thread attribution and call chains. The repository documents only 807 cycles:u samples in its earlier profile; __unlock, free and memcpy samples do not by themselves identify the calling allocation or explain total cgroup CPU. The daemon image uses musl plus the system allocator. If allocator work remains dominant, use the existing allocator switches or a matched GNU/musl build as controlled experiments, with the same source and memory measurements.
6. Only after a source change shows a repeatable paired benefit, run the comparative suite. Use alternating baseline/candidate trials at 4, 32 and a higher feasible MiB/s, plus uncapped throughput separately. Compare fresh idle, post-transfer idle, active upload, completed controlled download and multiple loaded torrents. Caps are memory limits, not evidence of actual residency; capped completion times are not maximum-throughput results.

This is promising enough to justify the architecture work, but current evidence does not establish the desired CPU/RAM advantage. The new tests explain why another isolated allocation or cap adjustment is unlikely to finish the job.
