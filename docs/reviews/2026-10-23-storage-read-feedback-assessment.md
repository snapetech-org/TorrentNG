# Storage-read performance feedback assessment — 2026-10-23

## Scope and source

The checkout is synced to the canonical GitHub `origin/main` at `2e5b88f21491a31c282efba60461d1566c50c456`. There is no Git remote named `upstream`; `origin/main` is the tracked project main branch. The worktree was clean before this review.

This review checked the feedback against the current upload-read implementation, the archived seed CPU profiles, the current client comparison, prior candidate results, and a narrow Linux `preadv2(RWF_NOWAIT)` feasibility probe. It does not claim a whole-client performance result.

## Findings

| Feedback claim | Assessment | Evidence and action |
|---|---|---|
| The current comparison is too short and noisy for small CPU changes. | **Valid.** | The latest five-client screen transfers 64 MiB at a 4 MiB/s receiver cap, about 16 seconds of payload time, in three rounds. It reports high host I/O pressure and wide per-round CPU ranges. At 4.17 CPU-s/GiB, that is roughly 0.26 CPU-seconds for one 64 MiB TorrentNG transfer. Add operation counters and use longer, randomized matched runs before judging small CPU deltas. |
| The rTorrent CPU result varies 2.9× between harnesses. | **Not an apples-to-apples variance estimate.** | The cited values use different reports, measurement windows, and rTorrent versions: the October 24 screen reports 0.85 active CPU-s/GiB for rTorrent 0.16.26; the October 23 qualification reports 2.439 CPU-s/GiB for rTorrent 0.16.25 over its qualification window. The difference is a reason to reconcile definitions and run a common harness, not proof that one identical comparator fluctuated 2.9×. |
| The benchmark omits instructions, cycles, context switches, and syscall counts. | **Valid.** | The current harness records cgroup CPU and block-I/O counters, memory categories, and transfer progress. It does not record hardware instruction/cycle counts or process context-switch/syscall counts. On this host (`kspld0`), `perf`, `strace`, and `bpftrace` are not installed; `perf_event_paranoid` is `2`. Keep syscall tracing out of scored runs because ptrace-based tracing changes the workload. First make counters available in a diagnostic run on a host that permits them, then keep clean scoring runs untraced. |
| Each default `pread` upload batch makes a storage-worker round trip, including peer-read cache hits. | **Mechanism confirmed; CPU impact unproven.** | `read_upload_batch_blocks` calls `read_owned_at_with_priority` for the buffered path. When the selected backend uses pread workers, that calls `run_reusable` for every read. `PreparedPread::execute` checks the peer-read cache on the worker and checks the current path identity before returning a cache hit. The async completion then resumes the caller. This establishes one worker submission/completion path per batch, including cache hits. It does **not** establish exactly two context switches, futex wakeups per batch, or that this path dominates CPU. |
| The old profile shows futex wakeups are the main cause. | **Unsupported by the profile.** | The 161-sample profile reports `syscall` at 12.4%, `epoll_wait` at 8.7%, `statx` at 5.6%, `pread64` at 5.6%, and `writev` at 11.2%. It does not identify the generic `syscall` samples as futexes or count context switches. A separate gperftools report resolves `PreparedPread::execute` to 2.9% of TorrentNG leaf samples and the prepared pread worker closure to 2.3%; those samples are diagnostic and do not prove the path is free or dominant. Measure the operation and wake counts directly. |
| Inline `preadv2(RWF_NOWAIT)` could bypass the worker on warm data. | **Worth a narrow, gated prototype after instrumentation.** | `RWF_NOWAIT` is Linux-specific and best-effort: it can return `EAGAIN` when the operation would wait, and may return a partial read. Kernel documentation describes this as avoiding operations that could block, not as a universal filesystem guarantee. On `kspld0` (Linux 7.1.7, Btrfs), an initial warm-read probe returned `EAGAIN`; after a normal read warmed the range, 1,000 repeated 16 KiB `preadv2(RWF_NOWAIT)` calls on both `Cargo.lock` and `/usr/bin/python3` returned all bytes and matched the expected data. Each loop took about 2 ms in a Python/ctypes probe; this is only an API feasibility check, not a performance comparison. Any prototype must fall back on `EAGAIN`, unsupported flags/filesystems, zero or short reads, and errors, and keep the blocking read on the existing worker path. |
| Relax path identity checks to once per interval. | **Do not add this setting yet.** | The existing path check fences cached descriptors and read-cache ranges against a replaced path. The project’s prior seed-path review explicitly treats that as a correctness and security invariant. The old profile’s `statx` share is not sufficient evidence to weaken it. First test an inline warm-cache route while retaining the same validation contract; revisit validation frequency only if measured cost remains material and the safety semantics are redesigned explicitly. |
| Re-screen current-thread Tokio and the 32 ms/eight-block window. | **Reasonable follow-up, not a default change.** | The archived current-thread runtime screen lost one 64 MiB round by 8.1% CPU and added 0.32 MiB PSS versus the one-worker multithread control; it was order-confounded and remains unpromoted. The existing 32 ms/eight-block setting has prior positive screens, but its batch timing is close to the 4 MiB/s workload. Re-screen both only after measuring the worker path, using several rates and one- and multi-peer shapes. Keep the old results and patches for comparison. |
| Try non-PIE for anonymous memory. | **Possible later memory-only experiment.** | Earlier mapping analysis found roughly 628 KiB of anonymous read-only executable pages attributed to relocations. This is small relative to the remaining resource gap and says nothing about CPU. Keep it separate and opt-in if tested; report the address-space-randomization tradeoff and compare PSS and anonymous memory independently. |
| Add 10k–100k-torrent idle and multi-peer tests. | **Valid, separate scalability gate.** | The documented product scale target is not represented by the current one-torrent seed comparison. Add staged idle-library and multi-peer cases as a separate scale track; do not mix their results into CPU-s/GiB for one active seed. Measure the per-torrent timers, actor state, and memory growth before expanding to the largest catalog sizes. |

## Recommended next sequence

1. Add diagnostic counters for upload batch count and size, peer-read cache hits/misses, prepared worker submissions, path-identity checks, and backend reads. Normalize each by verified payload GiB.
2. On a host with usable perf events, collect instructions, cycles, context switches, and migrations per verified GiB. Collect syscall counts in a separate diagnostic pass and label the tracing method and its overhead. Do not put traced values in the clean CPU score table.
3. Start with a small current-main versus rTorrent probe using the same source fixture, storage path, CPU affinity, runtime, rate, and active-transfer boundaries. Extend the fixture or duration only if the diagnostic counters have enough work to distinguish candidates.
4. If the counters show meaningful per-batch worker cost, prototype an opt-in warm-page-cache `RWF_NOWAIT` path for already-open, identity-bound file handles. Keep the worker fallback and current identity fence. Test cached hits, cold/missing pages, partial and zero results, unsupported filesystems/kernels, cancellation, and byte-for-byte transfer correctness before measuring CPU and RAM.
5. Re-screen runtime and coalescing choices at multiple rates and peer counts. Keep each candidate and its measured losses available for later combinations.
6. Track many-torrent idle and multi-peer scale independently from the single-seed resource comparison.

No production defaults or path-identity guarantees changed in this review.
